We have reached a solid phrase-streaming prototype. The avatar now looks convincing, lip-sync is substantially improved, and the system is measurable and repeatable. It is not yet a continuously streaming, sub-second real-time avatar.

## **What worked particularly well**

* Chatterbox Turbo significantly reduced local TTS delay. Resemble describes Turbo as its efficient low-latency English voice-agent model, with a smaller 350M architecture and single-step decoder. [Official Chatterbox repository](https://github.com/resemble-ai/chatterbox?utm_source=chatgpt.com)  
* Preset voice cloning eliminated much of the voice variation between phrases.  
* Direct-memory JoyVASA → FLP rendering removed considerable file and FFmpeg overhead.  
* Stride 2 made the FLP renderer approximately compatible with its measured throughput:  
  * FLP rendering: approximately `11–12` new frames/second.  
  * Stride-2 playback requirement: `12.5` new frames/second.  
  * Stride-3 catch-up: `8.33` new frames/second.  
* Adaptive stride 2→3 protects playback when the buffer becomes low.  
* Adaptive TTS prefetch avoids the severe renderer slowdown we observed with eager concurrent TTS.  
* The first-video-window audio gate corrected the large initial A/V offset.  
* `animation_region=all`, multiplier `1.0`, normalization enabled and retargeting disabled produced the most dependable face.  
* Disabling paste-back avoided the cuSOLVER instability.  
* The quality/runtime benchmark separation explained why stride 1 could look good offline but could not remain synchronized during streaming.

## **Recommended real-time configuration**

This is the best current single-RTX-5080 configuration:

```
TTS_PROVIDER=chatterbox
CHATTERBOX_VARIANT=turbo
TTS_DEFAULT_VOICE_MODE=preset-clone

AVATAR_INCREMENTAL_FRAME_WINDOWS=true
AVATAR_RENDER_WINDOW_FRAMES=8
AVATAR_RENDER_STRIDE=2
AVATAR_ADAPTIVE_RENDER_STRIDE=true
AVATAR_CATCHUP_RENDER_STRIDE=3
AVATAR_CATCHUP_BUFFER_SECONDS=0.75

AVATAR_TTS_PREFETCH=true
AVATAR_TTS_PREFETCH_POLICY=adaptive
AVATAR_TTS_PREFETCH_MIN_BUFFER_SECONDS=0.50

AVATAR_PERSISTENT_PHRASE_MOTION=true
AVATAR_RELATIVE_MOTION=true
AVATAR_USE_NEURAL_IDLE_FRAME=true

AVATAR_ANIMATION_REGION=all
AVATAR_DRIVING_MULTIPLIER=1.0
AVATAR_NORMALIZE_LIP=true
AVATAR_EYE_RETARGETING=false
AVATAR_LIP_RETARGETING=false
```

And internally:

```
DIRECT_MEMORY_RENDER=true
AVATAR_PASTE_BACK=false
```

This gives the best balance of:

* Facial character.  
* Lip-sync.  
* Voice consistency.  
* Startup latency.  
* Sustained playback.  
* GPU stability.

It is “real-time phrase streaming”: once a phrase is available, playback starts progressively while later phrases are prepared.

It is not yet “continuous streaming”: a phrase must still pass through TTS and JoyVASA motion generation before the first FLP window can appear.

One benchmark nuance: the `runtime` quality test disables TTS prefetch deliberately to isolate visual performance. For normal interactive use, keep adaptive prefetch enabled.

## **Recommended non-real-time/high-quality configuration**

Use this for demos or generated clips where waiting is acceptable:

```
AVATAR_RENDER_STRIDE=1
AVATAR_ADAPTIVE_RENDER_STRIDE=false
AVATAR_INCREMENTAL_FRAME_WINDOWS=false
AVATAR_TTS_PREFETCH=false

AVATAR_ANIMATION_REGION=all
AVATAR_DRIVING_MULTIPLIER=1.0
AVATAR_NORMALIZE_LIP=true
AVATAR_EYE_RETARGETING=false
AVATAR_LIP_RETARGETING=false
```

This renders all 25 motion frames per second before synchronized playback. It produces smoother facial motion but takes approximately twice the media duration to render because FLP currently achieves only around 11.5 neural FPS.

For TTS:

* Choose Chatterbox Turbo for fast English generation and the established cloned voice.  
* Choose Breeze when its voice quality is preferred and generation time is not critical.  
* Keep lip retargeting disabled; it produced black output on this portrait.

## **What still prevents true real-time operation**

### **1\. FLP rendering throughput**

The primary sustained bottleneck is:

```
Required at stride 1: 25 FPS
Measured FLP rendering: approximately 11–12 FPS
```

Stride 2 hides most of that limitation, but it reduces temporal detail and leaves little safety margin.

FasterLivePortrait reports over 30 FPS using TensorRT on an RTX 3090\. However, its documented path uses TensorRT 8.x and a custom 3D GridSample plugin; the RTX 5080 will likely require newer TensorRT and custom engine/plugin conversion, so compatibility must be tested rather than assumed. [FasterLivePortrait repository](https://github.com/warmshao/FasterLivePortrait?utm_source=chatgpt.com)

### **2\. JoyVASA requires a completed phrase**

FLP frame windows are incremental, but JoyVASA still creates the motion sequence from a completed phrase WAV. Therefore:

```
text phrase
→ complete TTS audio
→ complete JoyVASA motion
→ first FLP window
→ WebRTC playback
```

We improved the final two stages, but the first two remain batch-oriented.

### **3\. Chatterbox is faster-than-real-time, but not chunk-streaming in our adapter**

Chatterbox Turbo is optimized for low latency, but its documented Python interface returns a generated waveform from `model.generate(...)`; its official repository does not currently document a chunk-streaming generation API. [Official Chatterbox usage](https://github.com/resemble-ai/chatterbox?utm_source=chatgpt.com)

Our HTTP adapter consequently returns one completed phrase waveform. Smaller phrases reduce delay, but very small phrases can create unnatural prosody and voice discontinuities.

### **4\. Shared-GPU contention**

TTS and FLP compete for the same 5080:

* Eager TTS overlap previously reduced rendering from approximately 12 FPS to around 6 FPS.  
* Adaptive prefetch protects FLP, but it cannot create additional GPU capacity.

### **5\. Phrase boundaries**

Persistent motion state improves continuity, but each phrase is still an independent TTS and JoyVASA request. This can cause:

* Prosody changes.  
* Short pauses.  
* Expression discontinuity.  
* Different motion energy between phrases.

## **Recommended next steps**

### **Step 1 — Freeze and measure the current baseline**

Run at least three repeats using the realistic runtime profile:

```
QUALITY_BENCHMARK_PROFILE=runtime \
QUALITY_BENCHMARK_SCENARIOS='baseline,all,1.0,true,false,false' \
QUALITY_BENCHMARK_REPEATS=3 \
./quality_benchmark.sh
```

Test three fixed inputs:

* One short sentence.  
* Three normal sentences.  
* A longer 15–20 second answer.

Suggested acceptance targets:

| Metric | Initial target |
| ----- | ----- |
| First audible/visible response | under 1.5–2.0 seconds |
| A/V offset | under approximately 120 ms |
| Audio gaps after playback begins | under 150 ms |
| Video holds | no obvious hold longer than 200 ms |
| Neural renderer | consistently above 12.5 FPS, or catch-up without visible disruption |

We should also automate mouth-aperture versus audio-envelope correlation, turning lip-sync assessment into a recorded metric rather than relying entirely on watching every MP4.

### **Step 2 — Move TTS to the RTX 4080 laptop**

This is the lowest-risk next performance experiment.

Recommended topology:

| Machine | Work |
| ----- | ----- |
| RTX 4080 laptop | Chatterbox or Breeze TTS HTTP service |
| RTX 5080 laptop | JoyVASA, FLP, FastAPI and WebRTC |

The audio network traffic is tiny compared with video inference, so LAN overhead should be negligible. The benefit is that TTS can generate the next phrase without reducing FLP neural FPS.

The current application already uses `TTS_URL`, but Compose needs a clean “external TTS” mode so it does not require or start the local `tts` container.

Measure the same three-repeat baseline before and after splitting. Keep the split only if it improves gaps or first-ready latency.

### **Step 3 — Time-box FLP acceleration**

Before replacing FLP, profile:

* Warping/decoder model time.  
* CPU↔GPU copies.  
* ONNX Runtime provider selection.  
* CUDA I/O binding opportunities.  
* FP16 compatibility.  
* TensorRT engine/plugin feasibility on the RTX 5080\.

Goal:

```
Minimum: stable >15 unique FPS
Ideal: stable ≥25 unique FPS
```

If we cannot reach approximately 20–25 FPS without fragile patches, stop investing heavily in the FLP real-time path.

### **Step 4 — Add true audio/motion chunking**

A genuine streaming pipeline should look like:

```
TTS PCM chunks
→ rolling audio-feature window
→ stateful motion chunks
→ FLP/Ditto frames
→ bounded WebRTC queue
```

That requires:

* Roughly 200–500 ms PCM chunks.  
* Overlapping audio context.  
* Persistent motion state.  
* Boundary blending.  
* Backpressure when rendering falls behind.  
* One shared A/V clock.  
* Cancellation when the user interrupts speech.

JoyVASA does not presently provide this clean online contract in our integration. Retrofitting it is possible, but substantial.

### **Step 5 — Build a Ditto online proof of concept**

Ditto now has an official `stream_pipeline_online.py`, an online configuration, ONNX models and TensorRT engines. Its supplied engines target Ampere-plus hardware, and the project documents converting ONNX models to custom TensorRT engines when the provided engines are incompatible. [Official Ditto repository](https://github.com/antgroup/ditto-talkinghead?utm_source=chatgpt.com)

This should be a parallel renderer experiment, not an immediate rewrite:

1. Keep the existing TTS provider interface.  
2. Keep FastAPI, aiortc, HTML and benchmark protocol.  
3. Replace only JoyVASA \+ FLP with Ditto online.  
4. Feed the same fixed audio fixture.  
5. Compare:  
   * First frame latency.  
   * Sustained FPS.  
   * A/V offset.  
   * Face identity.  
   * Mouth quality.  
   * VRAM.  
   * Stability on the RTX 5080\.

If Ditto delivers stable online frames on the 5080, it becomes the likely production real-time renderer. If not, the current FLP phrase-streaming implementation remains a good fallback.

## **My recommended order**

1. Lock v2N.2.1 as the working FLP baseline.  
2. Add objective lip-sync measurement to the benchmark.  
3. Add external-TTS mode and test the 4080/5080 split.  
4. Profile FLP and run one time-boxed TensorRT/FP16 experiment.  
5. In parallel, start a minimal Ditto online renderer benchmark.  
6. Choose between accelerated FLP and Ditto using identical recorded tests.  
7. Only then add microphone/LLM interruption and fully conversational behavior.

The most sensible immediate next version is therefore: **external TTS mode for the 4080 plus objective A/V-offset measurement**, while preserving the current working 5080 FLP baseline.
